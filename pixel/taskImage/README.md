# Задание: Image / Pixel / TemplateImage

## Что делает программа

Программа показывает работу классов `Image` и `TemplateImage` — хранение изображения как динамического массива пикселей.

## Структура файлов

| Файл | Что внутри |
|------|-----------|
| `Pixel.h` | Структура пикселя (r, g, b) |
| `Image.h` | Объявление класса Image |
| `Image.cpp` | Реализация Image: Rule of 5, операторы, static |
| `TemplateImage.h` | Объявление наследника |
| `TemplateImage.cpp` | Реализация — заполнение чёрным |
| `main.cpp` | Демонстрация copy vs move и всех операторов |
| `Makefile` | Сборка проекта |

## Классы

### Pixel
Простая структура — три поля `r`, `g`, `b` типа `unsigned char` (0..255).

### Image
Хранит пиксели в динамическом массиве `Pixel* data`.

**Rule of 5:**
- Конструктор — выделяет память `new Pixel[w*h]`
- Деструктор — освобождает память `delete[] data`
- Копирующий конструктор — создаёт новый массив и копирует пиксели
- Копирующее присваивание — то же самое, но сначала удаляет старое
- Перемещающий конструктор — забирает указатель, у источника ставит `nullptr`
- Перемещающее присваивание — то же самое

**Операторы:**
- `operator()` — доступ к пикселю по координатам `img(x, y)`
- `operator+` — поэлементное сложение каналов, результат не больше 255
- `operator==` — сравнение размеров и всех пикселей
- `operator<<` — вывод размера и первых пикселей

**Static:**
- `count` — считает сколько объектов Image живёт прямо сейчас
- `getCount()` — возвращает count

### TemplateImage
Наследник `Image`. Конструктор вызывает `Image(w, h)` и заполняет все пиксели чёрным `{0, 0, 0}`.

## Сборка и запуск

```bash
make
./image
```

## Ожидаемый вывод (порядок логов)

```
Inside Constructor       <- Image a(4,4)
Inside Copy Constructor  <- Image b = a
Inside Move Constructor  <- Image c = std::move(a)
Inside Constructor       <- Image d(4,4)
Inside Copy Assignment   <- d = b
Inside Constructor       <- Image e(4,4)
Inside Move Assignment   <- e = std::move(b)
...
Inside Destructor        <- все объекты при выходе из main
```


Что требовало ТЗ                                                                                                                              
                                                                                                                                                ы
  1. Класс Pixel                                                                                                                             
  Структура с тремя полями — красный, зелёный, синий канал.

  2. Класс Image с динамической памятью
  Хранить пиксели не в vector, а в сыром указателе Pixel* data. Выделять через new, освобождать через delete[]. Это учит управлять памятью
  вручную.

  3. Rule of 5
  Если класс управляет памятью — нужно написать все 5 специальных методов:
  - конструктор
  - деструктор
  - копирующий конструктор
  - копирующее присваивание
  - перемещающий конструктор
  - перемещающее присваивание

  Иначе компилятор сгенерирует их неправильно — будет shallow copy (оба объекта указывают на один массив → двойной delete → crash).

  4. Доступ к пикселям двумя способами
  at(x, y) и operator()(x, y) — оба в const и non-const версиях.

  5. Перегрузка операторов
  - + — сложить два изображения поканально
  - == — сравнить
  - << — вывести в cout

  6. static и const
  - static int count — счётчик живых объектов, общий для всех экземпляров
  - const методы — методы которые не меняют объект (getWidth, at const)

  7. Класс TemplateImage : public Image
  Наследник, который при создании заполняет всё чёрным. Показывает как вызывать базовый конструктор через : Image(w, h).

  8. main() с демонстрацией copy vs move
  Показать на практике разницу: copy делает новый массив, move просто передаёт указатель. Терминал должен печатать Inside Copy Constructor,
  Inside Move Constructor и т.д. — чтобы было видно когда что вызывается.

  ---
  Зачем это всё

  ТЗ учит одной важной теме — управление ресурсами в C++. Когда у класса есть сырая память, нужно явно контролировать что происходит при
  копировании и перемещении. Move семантика (std::move) нужна для производительности — не копировать большой массив, а просто передать владение
  указателем.



    ---                                                                                                                                           
  Inside Constructor — Живых объектов: 1
  Image a(4,4) вызвал конструктор. Выделилась память под 16 пикселей. count стал 1.                                                             
                                                                                                                                             
  ---                                    
  Inside Copy Constructor — Живых объектов: 2
  Image b = a — создаётся новый объект из существующего. Выделился новый массив, пиксели скопированы из a. Теперь a и b — независимые куски
  памяти. count = 2.

  ---
  Inside Move Constructor — a.getWidth() после move: 0
  Image c = std::move(a) — памятьне копировалась. c забрал указатель data у a. У a теперь data = nullptr, width = 0. Поэтому a.getWidth()
  возвращает 0. Быстрее копирования — никакого new.

  ---
  Inside Constructor + Inside Copy Assignment
  Image d(4,4) — создали пустой объект (Constructor).
  d = b — присвоили данные из b в уже существующий d (Copy Assignment, не конструктор). Два отдельных события.

  ---
  Inside Constructor + Inside Move Assignment
  То же самое — сначала Image e(4,4), потом e = std::move(b). Move Assignment забрал данные из b.

  ---
  Inside Constructor — operator+
  c + d внутри создаёт новый Image result(width, height) для хранения суммы. Отсюда один Constructor.

  ---
  c == d: true
  Оба 4x4, содержимое одинаковое — operator== прошёл по всем пикселям, всё совпало.

  ---
  operator<< — вывод пикселей
  pixel[0] = (255, 0, 0) — чисто красный.
  pixel[1] = (0, 255, 0) — чисто зелёный.
  pixel[2] = (0, 0, 255) — чисто синий.
  pixel[3] = (200, 100, 50) — тёмно-оранжевый.
  pixel[4..8] = (0,0,0) — не заполняли, остались нулями (память new не инициализируется, но здесь Pixel — POD тип, и компилятор обнулил через
  value-init).

  ---
  TemplateImage — все (0,0,0)
  TemplateImage t(3,3) вызвал Image(3,3) (отсюда Constructor), потом цикл заполнил все 9 пикселей чёрным явно.

  ---
  3x Inside Constructor в секции clamp
  Image x(1,1) — Constructor.
  Image y(1,1) — Constructor.
  Image z = x + y — внутри operator+ создался result(1,1) — ещё Constructor.
  Итого 3.

  ---
  10x Inside Destructor
  При выходе из main все локальные объекты уничтожаются в обратном порядке создания. Каждый вызывает delete[] data и печатает строку. Объектов
  было 10 — деструкторов тоже 10. count вернулся в 0.
